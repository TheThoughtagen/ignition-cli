# Quick 261030-8m8: Code Review Report

**Reviewed:** 2026-10-30T15:55:36Z
**Depth:** quick. The diff was also read in full along the five focus areas, and the plan engine, apply gates, transport mirror validation and exclusion code it depends on were traced.
**Files Reviewed:** 15 (the `captured-cd5/` fixtures count as one entry)
**Status:** issues_found

## Summary

The mapping change in `layout.rs` is correct. `collection_path` and `repo_path` are exact inverses for every tag type, every tail depth and every non-tag path (see "Focus-area verdicts"). The CD5d folder-name check and the CD5c marker check echo no secret-bearing content. They name only fixed member names and a count, and the finding `file` is the operator's own repo path. Excluded providers and unreadable units stay out of the delete set at every new depth, and the new plan test covers this.

The main problems are in what the plan does *not* treat as destructive now that CD5c is proven. The gateway loads only the member files a marker lists, and a mode-collection tag unit hides its `core` copy. So a rendered tag unit that lacks a member file present live (in the mode collection or in `core`) removes those tags or UDT types from the running gateway. The plan reports this as a plain `changed`/`added` with no `destructive` flag, so `--allow-destructive` never gates it. This was already true for folder tags. The change now makes it reachable for the provider-root unit (root tags and root UDT instances) and for nested type folders (UDT types, whose loss breaks every instance using them). The CD5c render check also has fail-open gaps. The README documents them, but they let a deploy that the gateway silently ignores go through as `applied` with a green verify.

The shell drivers pin ssh/sftp host keys correctly (`StrictHostKeyChecking=yes`, pinned 0600 file, `GlobalKnownHostsFile=/dev/null`). Their HTTP halves have no gateway-identity guard. In `capture-cd5.sh` the localhost guard covers `curl` but not the `ign` calls, which honour an inherited `IGNITION_URL`.

## Focus-area verdicts

1. **Delete-set safety:** the file-level delete set is sound: ledger-only, mode-only, excluded and unreadable units skipped, case-fold guard kept. **The non-delete loss paths are not gated** (CR-01, CR-02).
2. **`check_tag_markers`:** the path handling is correct (`dir` is derived from a path that is guaranteed to end in the marker name, and `present` is resolved against rendered files). No content is echoed. Case handling is exact-byte for members and ASCII-folded for CD5d folders. Coverage gaps: WR-01, WR-02, WR-03.
3. **CD5d refusal:** this review found no bypass on the render side for Linux hosts. On Windows, trailing-dot and trailing-space spellings are caught later by `windows_component_problem` in the sftp transport. The refusal does not cover a *live* folder with a member name (WR-04), and non-ASCII case folding is untested (IN-02).
4. **`collection_path`/`repo_path` inverse:** correct. The proptest alphabet is narrow (IN-03).
5. **Shell drivers:** strict host keys are correct, and quoting is acceptable for the synthetic names used. There is no production-target guard on the HTTP/`ign` half of either driver (WR-05, WR-06).

## Critical Issues

### CR-01: A tag unit that drops a live member file is not destructive, so it removes tags from the running gateway with no gate

**File:** `crates/ignition-core/src/deploy/plan.rs:709` (also `:685`, `:492-570`)
**Issue:** `destructive = status == Removed || deleted_here > 0`. For tag units, CD5c (gateway loads only listed members) and CD5a S4 (a mode root unit hides the core root members) together mean that two cases remove tags from the running gateway without deleting any file:

- **Mode orphan.** The mode collection holds `ignition/tag-definition/P/udts.json`, and the declared-names ledger does not list it. This happens on a first deploy (no ledger), or when a file was written by hand or by an earlier tool. The rendered unit has a marker listing only `tags.json`. The plan shows the unit `changed`, with `udts.json` as a `PlanFile` whose `desired_sha256` is `None`. The delete set is empty, so `destructive` is false. Apply rewrites the marker. The orphan `udts.json` stays on disk but is no longer listed, so every root UDT instance disappears at the next scan. Render's CD5c check cannot see this case because it never sees live files.
- **Core hidden.** The core copy holds a root `udts.json`, or a nested type folder's `A/B/udts.json`, that the rendered mode unit lacks. The relation is `CoreRelation::Hidden`, but `evaluate_gates` (`apply/gates.rs:112-121`) only blocks `ShadowsRemoval` and `destructive`. `Hidden` appears only as a word in the confirmation prose. For CD5b this means UDT *types* vanish, which breaks every instance of them.

Before this change, the root unit could not carry `tags.json`/`udts.json` and nested type folders were refused, so neither shape could reach production.
**Fix:** Mark these entries destructive with `tag_data_loss`, using the CD5c rule in plan:

```rust
// in plan(), after core_relation is known
let drops_live_member = is_tag_folder(key)
    && effective.is_some_and(|e| {
        e.keys().any(|p| {
            let name = p.rsplit('/').next().unwrap_or("");
            matches!(name, "tags.json" | "udts.json") && !rendered_files.contains_key(p)
        })
    });
let hides_core = core_relation == CoreRelation::Hidden;
let destructive = status == PlanStatus::Removed
    || deleted_here > 0
    || (wanted.is_some() && (drops_live_member || hides_core));
```

Add plan tests for the provider-root unit, the nested `A/B` unit, and a first deploy with no ledger.

### CR-02: A first deploy of a tag unit over `core` reports `differs`, not `hidden`

**File:** `crates/ignition-core/src/deploy/plan.rs:685`
**Issue:** `Some(c) if is_tag_folder(key) && mode_copy.is_some() && hides(c, rendered_files) => Hidden`. An `added` tag unit has no mode copy yet, but after apply it *will* be the mode copy and will hide `core` by folder (CD5a S4, CD5-CTL). Take the first production deploy of `ignition/tag-type-definition/P/A/B` where the rendered unit is a `files: []` marker, or a root unit without `udts.json`, while `core` holds the member. The plan shows `added [differs]` and is not destructive. The reviewer gets no signal that core tags or types are about to vanish. The module doc (lines 46-49) and the unit test `hidden_tag_folder` only cover the `same` case with an existing mode copy.
**Fix:** Drop the `mode_copy.is_some()` condition for rendered units. A rendered tag unit always lands in the mode collection:

```rust
Some(c) if is_tag_folder(key) && wanted.is_some() && hides(c, rendered_files) => {
    CoreRelation::Hidden
}
```

Then gate it as in CR-01. Re-golden `plan_sha256` deliberately, because the `core` word is hashed.

## Warnings

### WR-01: A member file in a folder with no marker is accepted, deployed, and never loaded

**File:** `crates/ignition-core/src/deploy/render.rs:486-558`; `crates/ignition-core/src/deploy/plan.rs` test `cd5_unit_keys` (the "falls to the nearest marked ancestor" cases)
**Issue:** `check_tag_markers` iterates over markers only. Two inputs pass render: `tags/P/tag-type-definition/A/B/udts.json` with no `A/B/unary-resource.json`, and `tags/P/tag-definition/tags.json` with no root marker (the README example path, lines 2574-2577, shows exactly this). Apply writes the file into a mode folder that is not a resource, so the gateway ignores it. The plan also groups the file under the wrong unit. The desired layer keys `A/B/udts.json` to `A`, while `core` keys it to `A/B`. So `A` shows `changed`, `A/B` shows `unmanaged`, the apply reports `applied`, and verify is green. This is the same silent-partial outcome CD5c was added to refuse. The README calls it deliberate, but it is fail-open on production.
**Fix:** In `check_tag_markers`, also walk every rendered `tags.json`/`udts.json` under the two marked types and refuse one whose own directory has no rendered `unary-resource.json`. The message should be: "a tag member file needs a unary-resource.json in its own folder listing it (CD5c)". Update `tags_map_to_collection_paths` (deploy_render.rs:600-611), which relies on marker-less `FolderA/` and `A/B` members.

### WR-02: A marker with no `files` member, or one that is not a JSON object, skips the CD5c check

**File:** `crates/ignition-core/src/deploy/render.rs:497-499`
**Issue:** `let Some(listed) = node.get("files") else { continue; }`. `Node::get` returns `None` for a missing key *and* for a marker that is an array or a scalar, so `[]` or `"x"` as `unary-resource.json` passes silently. CD5c S5(i) showed that a marker which does not list a member causes the gateway to skip that member. `tags_map_to_collection_paths` already renders a root `tags.json` beside a `{}` marker. The justification ("every gateway-written marker carries one") covers pulled trees only, not hand-written ones.
**Fix:** Refuse fail-closed when the marker is not an object, or has no `files` while any member is present:

```rust
let Some(listed) = node.get("files") else {
    if !present.is_empty() || !matches!(node, Node::Obj(_)) {
        findings.push(/* "`files` is missing; the gateway loads only listed members (CD5c)" */);
    }
    continue;
};
```

(Compute `present` before this branch.)

### WR-03: The member check is exact-case, and other files beside a marker are not checked

**File:** `crates/ignition-core/src/deploy/render.rs:505-512, 524-529`
**Issue:** `present` only looks for the exact bytes `tags.json` and `udts.json`. A `Tags.json` or `UDTS.JSON` beside a `files: []` marker raises no finding. On Linux the gateway never loads it. On NTFS it is the same file as `tags.json` but unlisted, so it is skipped. Either way it deploys silently and is ignored. Any other file name (`notes.json`, `tags.json.bak`) under a tag folder also maps (`tag_collection_path` accepts any tail) and is written into production unused. This contrasts with the CD5d check, which folds case.
**Fix:** Refuse any rendered file under `ignition/{tag-definition,tag-type-definition}/<P>/...` whose name is not exactly `tags.json`, `udts.json` or `unary-resource.json`. This subsumes the case variants and removes the "silently skipped" class altogether.

### WR-04: CD5d only checks the rendered side, so a gateway-created folder named `tags.json` in the mode collection is not refused

**File:** `crates/ignition-core/src/deploy/render.rs:379-391`; `crates/ignition-core/src/deploy/transport/mod.rs:662-711`
**Issue:** CD5d proves that the gateway itself creates a directory `ignition/tag-definition/<P>/tags.json/` (via import or the Designer) and then loses the root file. Suppose the repo now renders the CD5a root `tags.json` while the live mode collection holds that directory. `validate_mirror_paths` only checks staged and deleted paths against *each other*, not against the live listing. The plan treats the unit `.../P/tags.json` as `unmanaged` and the root file as a normal write. The clash is only discovered when the commit's rename onto a directory fails mid-apply, which depends on rollback rather than a pre-flight refusal.
**Fix:** In `plan` (or in the apply pre-flight), refuse when any staged file path equals a directory prefix of an observed mode or core path, or the reverse. Reuse the `dirs` logic of `validate_mirror_paths` over `rendered.files ∪ observed.mode.keys()`.

### WR-05: `capture-cd5.sh`'s LOCALHOST-ONLY guard does not cover the `ign` calls

**File:** `crates/ignition-core/tests/fixtures/live-rig-deploy/capture-cd5.sh:30-61, 84, 635`
**Issue:** `assert_local` validates `BASE`, which only `curl` uses. Every `ign --profile cd5-rig` call (provider create, the imports, `--yes tags provider delete`, `logs`) resolves the URL with the locked precedence flag > `IGNITION_URL` > profile (`session.rs:29`). The script never unsets `IGNITION_URL`. The Windows run env (`vmenv.sh`) exports `IGNITION_URL=http://52.154.75.231:8088`, so running this driver in the same shell sends the rig token (`IGN_CD5_TOKEN`) over plain HTTP to that host and attempts the writes there. `run`, `seed` and `clean` also never re-check that the profile URL inside `$STATE/cd5-ign-config.toml` is local; only `header` writes that file.
**Fix:** Run `unset IGNITION_URL` right after `assert_local`. Pass `--url "$BASE"` (or the flag equivalent) on every `ign` call, or re-run `ign_cfg` at the start of `run`, `seed` and `clean`.

### WR-06: `capture22w.sh` CD5-W has no gateway-identity guard on its HTTP half, and its prose claims a setting the script never makes

**File:** `crates/ignition-core/tests/fixtures/wflwvm01/capture22w.sh:305-308, 1128-1136, 1170`
**Issue:** The ssh/sftp half is pinned by host key. The `ign` half (`ign_json`/`icap`) goes to whatever `$PROFILE`, or an inherited `IGNITION_URL`, resolves to. The section prose says "`IGNITION_URL` set for the run to this address (P8)", but no line of the script sets or checks it (the only occurrence is that prose string). `cd5w` and `cd5wclean` then create providers, import tags, POST `scan/config`, and run `--yes tags provider delete`. Nothing asserts first that `gateway-info` names `Ignition-ignwin836` or that its address matches `$HOST`. That check happened only by hand (LIVE-CAPTURES line 5445). The VM's public IP is dynamic and the env file goes stale. If it does, the API token goes in cleartext (`http://…:8088`) to whatever host now holds the IP, or the writes hit any profile the operator mistyped, including a production one.
**Fix:** Before any write in `cd5w`, `cd5wseed` and `cd5wclean`, do two things. First, `export IGNITION_URL="http://$HOST:8088"` (or refuse unless `IGNITION_URL`'s host equals `$HOST`). Second, refuse unless `ign_json api call GET /data/api/v1/gateway-info | jq -r .data.result.data.name` equals an expected-name env var such as `IGN_WFLWVM01_GATEWAY_NAME`. Prefer https, or document the cleartext exposure.

## Info

### IN-01: Duplicate `files` entries are accepted silently

**File:** `crates/ignition-core/src/deploy/render.rs:522-530`
**Issue:** `names` is a `BTreeSet`, so `["tags.json","tags.json"]` passes. The gateway's behaviour with duplicate entries was not captured.
**Fix:** Count duplicates as `other` entries (refused, not echoed).

### IN-02: The CD5d case fold is ASCII-only

**File:** `crates/ignition-core/src/deploy/render.rs:466-472`
**Issue:** `eq_ignore_ascii_case` does not match `tagſ.json` (U+017F, which Java's `equalsIgnoreCase` treats as equal to `s`) or other Unicode case pairs. The CD5d collision is a file-system clash, and this review did not establish whether NTFS's upcase table folds U+017F. Low confidence that this is exploitable.
**Fix:** Refuse non-ASCII characters in tag folder names whose ASCII-only projection matches a member name, or note the limit in the CD5d comment.

### IN-03: The round-trip proptest alphabet is narrow

**File:** `crates/ignition-core/src/deploy/layout.rs:405-421`
**Issue:** `[A-Za-z0-9_]{1,12}` never generates spaces (`MQTT Engine` is a real excluded provider), dots, non-ASCII, or the member names themselves as folder segments, so the "exact inverse" claim is only tested over that subset.
**Fix:** Widen the strategy to `"[^/\\\\\\x00]{1,12}"` filtered through `RelPath::new`.

### IN-04: `capture-cd5.sh clean` deletes every empty directory under `production/ignition`

**File:** `crates/ignition-core/tests/fixtures/live-rig-deploy/capture-cd5.sh:628`
**Issue:** `find … -mindepth 1 -type d -empty -delete` also removes empty directories this driver did not create. `docker compose`/`docker exec` also follow any ambient `DOCKER_HOST`/`DOCKER_CONTEXT`, which the localhost guard does not check. Rig-only.
**Fix:** Delete only the `CAP5*` paths, and set `DOCKER_CONTEXT=default` (or refuse when `DOCKER_HOST` is set).

### IN-05: The CD5d analogue under `tag-provider` is not covered

**File:** `crates/ignition-core/src/deploy/render.rs:448` (`MARKED_TAG_TYPES`)
**Issue:** `tags/P/tag-provider/config.json/x.json` maps to a directory `ignition/tag-provider/P/config.json/` that clashes with the provider's own `config.json`. `validate_mirror_paths` catches this only when both paths are staged. The cause is the same as WR-04.
**Fix:** Apply the folder-named-like-a-file refusal to `tag-provider` (`config.json`, `resource.json`) as well.

### IN-06: A stray untracked script sits at the repository root

**File:** `svc-ignition-deploy@52.154.75ace-uat4.ps1` (untracked, not gitignored, dated 2026-10-26, outside this diff)
**Issue:** A PowerShell file whose name embeds the service account and part of the VM IP is one `git add -A` away from being committed.
**Fix:** Delete it, or move it out of the checkout.
