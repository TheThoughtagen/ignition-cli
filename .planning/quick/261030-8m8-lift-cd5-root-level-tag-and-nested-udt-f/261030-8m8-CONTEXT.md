# Quick Task 261030-8m8: Lift the CD5 refusals of root-level tags and nested UDT folders - Context

**Gathered:** 2026-10-30
**Status:** Ready for planning

<domain>
## Task Boundary

Let `ign deploy` manage the two tag layouts that decision CD5 left fail-closed, so production tags and UDTs come under declared config. This ships as v1.6.2.

The two layouts:

- **Root-level tags:** a `tags.json` or `udts.json` directly at `ignition/tag-definition/<provider>/`.
- **Nested UDT type folders:** folders below `ignition/tag-type-definition/<provider>/`, which are UDT types in sub-folders of `_types_`.

**Live evidence (2026-10-29):** `ign deploy pull --env production` against WIGNVM01 (8.3.6, Windows) skipped 79 units as `render_refused`. They are root-level tags in the providers `default`, `Gateway` and `Spark`, and 76 nested folders under `tag-type-definition`. The production tree is merged in WhiskeyHouse/whk-onprem-infra-iac under `ignition/gateways/wignvm01/`.

**Where the refusals live:** `crates/ignition-core/src/deploy/layout.rs::tag_collection_path`. They are also referenced in the `repo_path` docs, in `render.rs`, in the README's layout and skip-reason docs, and in tests.

**Out of scope:**
- Any write to production.
- The third CD5 refusal (any collection other than the default), which stays fail-closed.
- The MQTT Transmission long paths.
- A Cargo.toml version bump (release.yml stamps the version from the tag).
- Re-pulling production (see below).

</domain>

<decisions>
## Implementation Decisions

### Live capture first, code second
- The capture goes first, and the change depends on it. The code accepts a layout only when the capture proves both of these:
  - the on-disk layout the gateway writes for that layout;
  - that one config scan picks up a plain file-level write, change and delete at those paths, the same way C11 (23-LIVE-CAPTURES) showed for folder tags.
- **Capture rig (user: "Docker rig + Windows VM"):**
  - **Docker rig:** an 8.3.6 rig through `ign rig`. This is the main capture: layout bytes, plus scan pickup for write, change and delete.
  - **Windows test VM `ign-win-836`:** repeat the check over sftp as `svc-ignition-deploy`, the same transport and OS as production. Confirm the on-disk layout and the scan pickup there too, including the NTFS paths of nested `_types_` folders.
  - The VM has a dynamic IP. Read it with `az vm list-ip-addresses` after `az vm start`, and check that the pinned known_hosts entry covers it. Never use StrictHostKeyChecking=no. The daily auto-shutdown runs at 03:00 UTC.
- **The capture doc** is written in this task directory, in the style of 21/22/23-LIVE-CAPTURES. It gets decision IDs (for example CD5a for root-level tags and CD5b for nested UDT folders) that the code comments and README cite.
- **Data hygiene:** the rigs and the VM are disposable test hosts, and no production data is used. Never copy a production tag file into the repo or a fixture. Fixtures are synthetic.

### If a layout fails the scan-pickup check (user: "Read-only")
- If the gateway lays the files out as expected but a file-level write or delete isn't picked up the way folder tags are (it needs a provider restart, two scans, or it is ignored), the layout becomes **read-only**:
  - `pull` places the unit and `plan` diffs it.
  - `apply` refuses with a clear slug before any write, whenever this run would write or delete such a unit. Choose an existing exit-6 slug or add one under the four-place rule.
  - `verify` reports drift on it.
- If the capture can't even confirm the on-disk layout, that layout stays refused exactly as today.
- Read-only must be a per-layout flag in the layout mapping, not a special case spread across actions.

### Mapping invariants (from the task)
- `collection_path` and `repo_path` stay exact inverses for both new layouts. Proptest or table tests cover the round-trip.
- Pull places these units instead of skipping them as `render_refused`. A unit already ledgered or declared behaves like any other tag unit in plan, apply and verify: the delete-set safety, the ledger, the excluded providers and unreadable handling from v1.6.1.
- `plan_sha256` and the plan goldens are byte-identical for trees that contain neither layout.
- Contract parity:
  - the README tag layout table and skip-reason table;
  - the exit table, if a slug is added;
  - the golden and contract tests;
  - the secret canary, which must be unaffected.

### Production follow-up (user: "Re-pull later, separate PR")
- This task does not touch production. After the v1.6.2 release, a separate read-only pull of WIGNVM01 and an infra PR add the 79 units. The SUMMARY records this as the next step.

### Claude's Discretion
- The names: the decision IDs, the read-only flag, and the slug if one is needed.
- Whether the Windows VM pass reuses the Phase 22/23 capture harness or uses a smaller driver.
- How render treats a nested `tag-type-definition` folder: how `unary-resource.json` `files` lists relate across nesting levels, as the capture shows.

</decisions>

<specifics>
## Specific Ideas

- Model the capture on CD5's `C21-OQ4`/`C21-OQ1` (find listing plus per-file bytes) and on C11 (a plain file write into `production/`, one scan, read back through REST `tags/export`).
- **Scenarios** for each layout:
  - **create:** a root-level tag in a provider that also has folders, and a UDT type two levels deep under `_types_`;
  - **change:** edit a member;
  - **delete:** remove the file. Is the tag or type gone after one scan?
  - **round-trip:** the gateway-written bytes, then `ign deploy pull`, then `render`, then `plan` gives `has_changes: false`.
- Check what `unary-resource.json` at the provider root lists when root-level tags exist. CD5 saw `files: []` when there were none.
- Release v1.6.2 by pushing the tag, per RELEASING.md.

</specifics>
