<objective>
Make the downloads of a Windows deploy read cost a fixed, small number of transfers whatever the file count, and prove it at production scale.

After 261104-s3n the listing takes 2-3 PowerShell calls. `SftpTransport::fetch_files` still issues one sftp `get` per file. Measured live, that is about 0.37 s per `get`. The 14,270 files of the production-shape read take about 88 minutes, and one 10,000-file chunk passes the 1,050 s op timeout, so `ign deploy plan` fails with exit 4 (BRIEF Problem).

On a Windows host the read now fetches its files this way (BRIEF Fix):
- the exact FoundFile list goes up as one hash-checked list file
- one PowerShell call zips exactly those files into a fresh staging dir below the deploy account's home
- one sftp `get` downloads the archive, and the same session removes it
- the archive is extracted locally into the existing private download dir under the hostile-archive rules
- the existing `verify_download` runs unchanged

POSIX hosts are unchanged.

Purpose: a production-scale Windows read takes well under 2 minutes, so `plan`, `verify` and `apply` work on the production pair. The production-scale tests gate the download half of the transport the way they already gate the listing half.

Output:
- RED tests, then the fix
- the timed row
- the docs
- the live run: seed, the Rust read gate, the keychain checkpoint, then the timed plan and verify, and an exact restore
- SUMMARY
</objective>

<interfaces>
The bundle protocol, pinned here so the Task 1 fake (host side) and the Task 2 code (ign side) agree.

P1. Staging dir.
- The dir is `{home}/{ctl_name()}` in sftp spelling. `ctl_name` becomes `pub(super)`.
- Before any write, it is refused when it is at or below `data_dir` ignoring ASCII case. Detail: "the account home {home} is inside the data directory; a Windows read stages its archive in the account home, never below the data directory".

P2. Connections, in order, for a read with at least one file to fetch:
- (a) `account_home` (one `@pwd` session unless cached)
- (b) the upload session: `mkdir "{ctl}"`, then `put "<local list>" "{ctl}/read.tsv"`
- (c) one PowerShell call of BUNDLE
- (d) the get session: `get "{ctl}/read.zip" "<private archive dir>/read.zip"`, `rm "{ctl}/read.zip"`, `rmdir "{ctl}"`

No file to fetch means none of these. Any failure after (b) started is followed by one best-effort PowerShell call of BUNDLE_CLEAN. A production-shape read is then 3 listing + 4 = 7 connections. The bound is 8, which leaves one for a command-budget split of the listing.

P3. The list file (`read.tsv`).
- One line per file to fetch, in fetch order: `{size}` TAB `{collection}/{rel}` LF, UTF-8, no header.
- Names cannot hold TAB or LF: they passed safe_remote_path.

P4. BUNDLE params (JSON blob only):
- `x`: the prefix, `\\?\` on Windows and the empty string in local pwsh tests
- `b`: the native `<data_dir>\config\resources`
- `l`: the native list path
- `z`: the native archive path
- `h`: the lowercase hex SHA-256 of the list bytes
- `f`: free bytes required, `bundle::archive_limit + bundle::STAGING_FREE_MARGIN`

Result line:
- `{ok:1,n,z}`: n files bundled, z archive bytes
- `{ok:0,err:'list'}`
- `{ok:0,err:'space',free}`
- `{ok:0,err:'missing',i}`
- `{ok:0,err:'changed',i,n}`: n bytes copied

Host effects:
- On ok=1 the list is removed and the archive stays.
- On every other outcome (ok=0 or a terminating error), the list and any archive this call created are removed.
- An archive path that already exists is never written or removed (CreateNew).

P5. BUNDLE_CLEAN params: `x`, `d` (the native staging dir) and `f` (`["read.tsv","read.zip"]`).
- It removes each named regular file present in `d`, then `d` when it is empty. A missing `d` is ok=1.
- `{ok:0,err:'left'}`: `d` holds anything else, and nothing else is touched.
- `{ok:0,err:'reparse'}`: `d` is a reparse point, and nothing is touched.

P6. Archive entries are file entries only, named `{collection}/{rel}` with `/`, compressed with Deflate (CompressionLevel Optimal).

P7. The fake dispatches on parameter keys:
- `r` is an enumeration (existing; `Collections.Stack` still separates the recursive walk)
- `l` and `z` together are BUNDLE
- `d` and `f` together are BUNDLE_CLEAN
- `enum_fail` applies to enumerations only

P8. Detail wording. Every case is transport_failed, op "read". Task 1 tests assert these substrings, and Task 2 must produce them.

## Decisions (planner, decided from the code)

**D-dl1-1, container: zip built with `System.IO.Compression.ZipArchive`, not `tar.exe`.**
- No new dependency. `zip = 8.6` with the `deflate` feature is already a direct ignition-core dependency (Cargo.toml; used by project_artifact.rs and the apply `.gwbk` check), so this adds no crate and needs no package-legitimacy gate. A tar reader would add the `tar` crate or a hand-rolled parser, against the lean-tree constraint.
- No probe. `System.IO.Compression` ships with .NET Framework 4.5+ on every supported Windows Server. The walk already needs 4.6.2+ for its `\\?\` DirectoryInfo use, and pwsh 7 has it in-box. `tar.exe` is absent on Server 2016. Choosing it would need a probe plus a per-file fallback, and that fallback is the path that fails at production scale.
- No argument assembly. It is an in-process .NET API, so paths stay data in the JSON blob. There are no command-line arguments to quote for an external program.
- No assembly compile. `Add-Type -AssemblyName` loads a GAC assembly; nothing is compiled (unlike RECORD_REPLACE's csc.exe compile). It needs the FullLanguage session the walk already relies on. Use `ZipArchive` and `ZipArchiveEntry` from `System.IO.Compression` only, not `ZipFile` (which needs a second assembly).
- Smaller hostile surface. Zip has no hardlink or device entry type of its own (tar has hardlinks, symlinks, devices, and pax and GNU long-name records). Unix modes ride only in external attributes, which the extractor checks exactly.
- Less staging. Deflate shrinks the staged copy below the 48 MB tree, which matters on the 88%-full production disk.

**D-dl1-2, transfer path: one sftp `get` of the staged archive, not an uncapped ssh stream.**
- The process seam forbids file content on stdout. `process.rs` documents "File content never travels on stdout (it is downloaded to a temp dir), only listings", and `run_capped` buffers stdout in memory and kills the child at 32 MiB.
- An uncapped stream would need a new streaming method on the `ProcessRunner` trait. Every runner would have to implement it: TokioProcessRunner and the test runners (FakeSftp, FloodRunner, MvRunner, WinMoveRunner, OneExec, ...).
- Binary output over that seam is not proven. PowerShell 5.1 writes stdout in code page 437 (C7a-6), so raw binary over `exec_powershell` is unproven there. Base64 would add a third and still hit the cap for the 1 GiB READ_MAX_TOTAL_BYTES.
- `SftpOp::Get` is binary-safe and works live on this server. `run_download` already enforces a growth limit with kill, which BRIEF asks to reuse "sized for the compressed archive".
- Cost: two more connections than a stream (list upload and get, about 3.5 s each on this server), and one compressed copy staged in the home.

**D-dl1-3, staging place: `<home>/.ign-ctl-<nonce>/`, through the existing `ctl_name()`.**
- apply_ops.rs already uses this as the throw-away directory for "an operation that belongs to no staged run" (its layout doc, lines 19-23). That is the BRIEF's "home staging root (the same place existing staging uses)".
- A read has no gateway name or run id, so `ign-deploy/<gateway>/<mode>/staging/<run>` cannot be formed.
- The list upload follows run_ctl_in's mkdir-then-put pattern.

**D-dl1-4, always bundle on Windows when a read has a file to fetch.**
- This keeps one production code path on Windows and makes the cost independent of file count (BRIEF Fix).
- Accepted cost: a Windows read of a handful of files pays about three extra sessions compared with per-file. SUMMARY records it.
- The per-file path stays for POSIX, and stays as a test-only switch on Windows for the equivalence test.

**D-dl1-5, the generator's Prod content gets realistic compressibility.**
- Today `content()` pads with a repeated 16-character id, which deflate shrinks to well under 1% of 48 MB. A bundled transfer of it would not be "measured at real volume" (BRIEF test 1).
- The filler becomes words drawn by a fixed xorshift stream. The deflate ratio must land between 2x and 6x, which is less compressible than tag JSON with its repeated keys, so measured transfers are at or above production volume.
- The JSON stays valid and keeps its structure, so the live seed still suits a real gateway.
