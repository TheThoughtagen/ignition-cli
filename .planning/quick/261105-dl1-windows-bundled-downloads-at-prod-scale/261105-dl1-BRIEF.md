# 261105-dl1 brief: bundled Windows deploy-read downloads at production scale

Follows 261104-s3n (same branch `feat/windows-fast-listing`, 5 commits ahead of main). Read its SUMMARY first: `.planning/quick/261104-s3n-windows-fast-listing-at-prod-scale/261104-s3n-SUMMARY.md`.

## Problem

261104-s3n fixed listing on Windows (2-3 connections, 22 s live for the production-shape tree). Downloads are now the wall:

- `SftpTransport::fetch_files` (`crates/ignition-core/src/deploy/transport/sftp.rs` around line 1615) issues one sftp `get` per file, in chunks of at most `DOWNLOAD_CHUNK_FILES` (10,000) files / `DOWNLOAD_CHUNK_BYTES`.
- Measured live on ign-win-836: about 0.37-0.39 s per `get` inside one session. 14,270 files take about 88 min. One 10,000-file chunk (about 3,900 s) is far past the 1,050 s op timeout, so `ign deploy plan` failed with exit 4 `transport_failed` after 1,081 s.
- Windows OpenSSH sftp-server per-item overhead is server-side (the same server cost 0.8 s per folder `ls` on a LAN), so production will hit the same wall.

## Fix

On a Windows host, fetch the files of a read with a small constant number of transfers, independent of file count:

- Build one archive (or a small fixed number) of exactly the listed files on the host with one PowerShell call over ssh, transfer it in one sftp `get` (or one ssh stream that is not subject to the 32 MiB `STDOUT_CAP_BYTES` capture limit), extract locally, delete the remote archive.
- Choose the container format. `System.IO.Compression.ZipFile` (.NET 4.5+, present on every supported Windows Server) is preferred over `tar.exe` because it needs no probe. If you pick `tar.exe`, probe for it and fall back to the current per-file path when absent. Justify the choice in the PLAN.
- Stage the archive under the deploy account's home staging root (the same place existing staging uses), never under the gateway data dir. Remove it on success and on failure. The production master disk is about 88% full, so do not stage more than one copy of the tree (about 48 MB).
- POSIX hosts unchanged.

Safety properties to keep or add:

- The archive is built from the exact listed file set (the `FoundFile` list), not a re-walk. Files at 240+ chars stay excluded exactly as today.
- Local extraction refuses: absolute paths, `..`, drive letters, backslash tricks, symlink/hardlink/device entries, duplicate names, any entry not in the listed set, and missing listed entries. Extract into the existing private `download_dir`.
- Every extracted file must equal its listed size (the existing `check_chunk` semantics: "changed while it was read") and fit `READ_MAX_FILE_BYTES`. The total stays under `READ_MAX_TOTAL_BYTES`, checked before the transfer and enforced while it runs (the existing watch/kill pattern with `DOWNLOAD_SLACK_BYTES`, sized for the compressed archive).
- Decompressed size is bounded during extraction (zip bomb): stop at the listed total plus slack.
- Names that cannot be represented are handled the same as the listing path does today.
- The op timeout must comfortably cover a production-scale read. Do not raise the default timeout to paper over it.
- Same `ObservedFiles` output, same hashes as the per-file path for the same tree (prove with a test).
