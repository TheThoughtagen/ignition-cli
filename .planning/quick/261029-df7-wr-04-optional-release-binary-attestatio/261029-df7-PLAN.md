<objective>
Close WR-04 from `.planning/phases/25-guarded-project-deploy/25-REVIEW.md` with OPT-IN release-binary provenance. Today the deploy-projects actions check the downloaded `ign` asset only against a `.sha256` fetched from the same release. That proves integrity, not authenticity, and the binary then runs with the production write token and the deploy SSH key. The owner wants attestation available and plans to use it, but no caller may be required to.

Design decisions (planner discretion, recorded here so the executor does not re-litigate them):
- **The gate lives inside `shared:install-ign`, between the sha256 check and extraction.** The task says to verify "after the existing sha256 check", and the binary must not run (`--version`) before its provenance is checked: a binary that ran could already write to GITHUB_ENV. The harness requires `shared:install-ign` to be byte-identical in deploy-plan.yml, deploy-apply.yml and both actions (projects-test 2a, apply-test 2). The same lines therefore go into all four copies. The body reads the mode as `${IGN_VERIFY_ATTESTATION-false}` (no colon), so in deploy-plan.yml and deploy-apply.yml, which never set the variable, nothing changes, while an action caller who passes an empty value is refused. deploy-plan.yml and deploy-apply.yml get no new input: they do not call these actions and are out of scope.
- **The token never reaches the downloaded binary.** GH_TOKEN is set from github.token only when the input is `true` (expression gate in the action env), and the body runs `unset GH_TOKEN` before extraction in every mode.
- **Attestations come from a dedicated `attest` job in release.yml, not from the build matrix.** The build job runs third-party tag-pinned actions (Swatinem/rust-cache, actions-rust-lang/setup-rust-toolchain, softprops/action-gh-release). Giving that job id-token: write would let any of them mint an OIDC token that signs as release.yml. The attest job runs only the first-party attest action and the gh CLI, so it is the narrowest job scope for the two new permissions. It downloads the uploaded release assets and checks every archive against its .sha256 before it attests, so it attests exactly the bytes the release serves.
- **The action is pinned to `actions/attest-build-provenance@v4`**, a major tag like every other action in release.yml. Upstream notes that v4 is a wrapper over `actions/attest`. The task names attest-build-provenance, so that is what is used. Storage records (`artifact-metadata: write`) apply only with push-to-registry, so that permission is NOT added.
- **No permission is added to deploy-projects.yml.** A called workflow that requests a permission its caller did not grant fails for that caller. TheThoughtagen/ignition-cli is public, so the job's github.token can read its attestations without `attestations: read`.

Purpose: an attacker who replaces a release asset together with its `.sha256` is stopped by any caller who sets `verify-attestation: true`, and callers who do not set it see no change.
Output: two actions and three workflows changed, RELEASING.md and README documented, three harnesses extended, and the 25-REVIEW-FIX.md report updated.
</objective>
