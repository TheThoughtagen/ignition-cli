Code facts the planner verified (do not re-derive):

- `plan.rs` `plan()`: `deleted_here` counts delete-set paths per unit key over the mode key layer, and status is `(None, _) if deleted_here > 0 => PlanStatus::Removed`. Delete-set paths are always files present in `observed.mode` (`delete_set` skips any path not in `observed.mode`), grouped with the same `mode_layer` as the mode copy. So a `removed` entry always has a mode copy, `effective` is that mode copy, and the entry's `files` are exactly the mode copy's files, each with `live_sha256: Some(..)` and `desired_sha256: None`. Paths compare as exact bytes (`PlanFile.path` and `RelPath::as_str` are both the observed collection path).
- `delete_set` (plan.rs ~584) skips ledger files that are dot-prefixed or `GATEWAY_OWNED_FILES`, under an excluded provider, out of scope, in an unreadable unit, rendered, or a case-only twin of a rendered file. It never sees files the ledger does not list. Any of these can leave residue in a `removed` unit.
- `pair_tag_keys(entries: &[PlanEntry])` (plan.rs ~484) is called from `gates::pair_tags_refusal(plan: &DeployPlanResult, ..)` (gates.rs ~64; used by `evaluate_gates` step 4 and by `apply::run_apply` at apply/mod.rs ~832) and from `actions::deploy::pair_tags_warning(entries, mode)` (actions/deploy.rs ~456; called at ~427 as `pair_tags_warning(&planned.entries, mode)` where `planned: Plan` also holds `delete_set: DeleteSet`). `DeployPlanResult` already carries `delete_set: DeleteSet`. `DeleteSet { files: Vec<RelPath> }` lives in `deploy::transport` (already imported in plan.rs); `RelPath` lives in `deploy::layout`.
- `canonical_text` hashes entries' `files` and the delete set only. Changing `pair_tag_keys`'s signature touches neither, so `plan_sha256` and every golden stay byte-identical. Do NOT add a field to `PlanEntry`.
- Emptied-folder interplay: `transport::emptied_dir_floor` removes an emptied folder chain up to and including `ignition/tag-definition` / `ignition/tag-type-definition`. A `removed` unit whose mode files are all deleted therefore leaves no residue of its own. Child units are their own entries and are judged on their own status. `unmanaged` entries stay out of `pair_tag_keys` (not the deploy's, existing design).
- `evaluate_gates` runs the pair refusal (step 4) before the no-op return and before the destructive-flag gate. A pair plan is refused `deploy_pair_tags_refused` with or without `--allow-destructive`. A standalone residual plan needs `allow_destructive: true` to be Ready.
