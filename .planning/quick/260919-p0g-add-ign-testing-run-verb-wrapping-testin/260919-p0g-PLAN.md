## Two spec collisions resolved up front (read before writing code)

**C-1 — the red-run exit code is 6, not 5.** The task description names "the
gateway-state exit code (5)". In THIS repo the exit taxonomy is LOCKED and 5 is
`auth_rejected`; **target_state is 6** (`crates/ignition-core/src/error.rs` module
doc table, `docs/reference/exit-codes.md`, and the `README.md` table, cross-checked
in both directions by `exit_code_mapping_enumerated` and `readme_exit_table_agreement`).
The description's intent — "gateway state" — maps to **6**. Use 6. Do NOT renumber
anything.

**C-2 — a red run cannot use the error envelope.** `ErrorEnvelope` is LOCKED to
exactly `{ok, profile, error{code, message, endpoint, hint}}` — it has **no `data`
field** (`crates/ignition-core/src/error.rs`, the `ErrorEnvelope` doc comment says
changing the field set is a breaking change for agents). The spec asks for BOTH a
stable slug AND "the JSON envelope still carrying the full results data", which the
error envelope cannot do.

Resolution — reuse the **`ign lint --strict` precedent**, the repo's ONE sanctioned
success-path EXIT exception (`crates/ignition-cli/src/main.rs:483-493`): render the
**success** envelope carrying every result field, then return `ExitCode::from(6)`.
The stable slug rides the payload as `data.slug = "tests_failed"` alongside
`data.verdict = "passed"|"failed"`. This is also how every real test runner behaves
(full report on stdout, verdict in the exit code).

**Consequence (do not "helpfully" fix this):** because `tests_failed` is NOT a
`CoreError` variant, it MUST NOT be added to the exit-code table in `README.md` or
`docs/reference/exit-codes.md`. `readme_exit_table_agreement` cross-checks those
tables against the enum literals bidirectionally and a README slug with no enum
variant FAILS the suite. Document `tests_failed` in the commands table and prose only.

  <name>Task 2: Decide `--format junit|text` semantics</name>
  <decision>How should `ign testing run --format junit|text` behave?</decision>

  <context>
The spec says `--format json|junit|text` is "passed through in the POST body to the
route". Discovery found that passthrough does not compose with the rest of the spec:

Reading `crates/ignition-core/webdev/testing/.../testing/run/doPost.py`, the route
only sets the HTTP status and returns machine results on the **json** path. For
`junit` it returns raw XML (`content-type: application/xml`) and for `text` raw
`<pre>` text — **status stays 200 in both cases and neither body contains
`passed/failed/errors/total`**. So a straight passthrough means a red suite exits 0
in junit and text mode, which is the opposite of what a CI flag is for. It also
collides with the JSON envelope contract (`crates/ignition-cli/tests/contract_stdout_purity.rs`
pins the sanctioned raw-stdout exceptions; XML on stdout would be a new one).

Task 1 has already shipped the working `--discover` and green/red json paths, so this
decision only shapes the `--format` arm in Task 3.
  </context>
