# 261104-s3n brief: fast Windows deploy reads at production scale

## Problem

This was measured read-only on a production Windows pair running ign 1.6.6.

On a redundant pair, option A2 makes `deploy verify`, `plan` and `apply` list `core/ignition/tag-definition` and `core/ignition/tag-type-definition`. `SftpTransport::discover` (`crates/ignition-core/src/deploy/transport/sftp.rs`, around line 1298) walks the tree level by level. It opens one sftp session per level and runs `ls -la` on each folder.

Windows OpenSSH sftp-server is slow per folder:

| Folders in a level | Time |
|---|---|
| 1 | 3-4 s |
| 10 | 10 s |
| 46 | 38 s |

That works out to about 0.8 s per folder plus about 3.5 s overhead per session.

Production tree shape, captured read-only from the master:

| Tree | Files | Dirs | Max depth | Max fanout | Bytes | Paths ≥ 260 chars |
|---|---|---|---|---|---|---|
| `core/ignition/tag-definition` | 14,119 | 7,500 | 14 | 89 | 47.8 MB | 7 (max 271) |
| `core/ignition/tag-type-definition` | 156 | 85 | 5 | 15 | 3.7 MB | 0 |
| whole `core` | 15,815 | 8,362 | 16 | 106 | 62 MB | 7 |

The mode collection is tiny.

At these numbers one read takes about 100 minutes. `verify --node both` and `apply` take hours, and `apply` does several reads while holding the lock. `Get-ChildItem -Recurse -Force` over ssh walks the same tree (21,619 items) in 6 s.

## Fix

On a Windows host, enumerate each requested tree with one PowerShell call over ssh, or a small fixed number of calls. Do not list per level over sftp.

Reuse the existing winps machinery:
- `winps::enumerate`, `enumerate_children` and `enumerate_chunks`
- `LONG_PATH_PREFIX`
- the `cross_check` / `enumerate_roots` path

The session count must be O(1) in tree size.

Keep every existing safety property:
- Refuse symlinks and reparse points, junctions included.
- Refuse anything that is not a file or a directory.
- Keep the required `config` and `config/resources` check.
- Keep the `READ_MAX_ENTRIES` budget and its exact error detail.
- List long-path (≥ 260) entries. Never drop them.
- Keep the N2 probe of requested folders.
- Refuse names that cannot be represented, or skip them when lenient.
- Report file sizes.
- Produce the same `TreeListing` / `Found` output.

POSIX hosts stay unchanged unless the same change is clearly safe there. Do not widen scope.

File content reads (downloads) are out of scope. Measure their session count at prod scale and report it in SUMMARY. Do not fix them silently.

## Production-scale testing (required)

The user asked for this explicitly: "make sure our tests for IGN-cli are actually at a production scale. We've done this shit a few times now."

1. **Fixture generator.** Write a deterministic generator as a test helper, not checked-in data blobs. It builds the prod shape above:
   - at least 14,119 files and 7,500 dirs under tag-definition
   - depth 14
   - one folder with fanout 89
   - at least 7 paths of 260 chars or more, measured as the full Windows path under a typical `C:\Program Files\Inductive Automation\Ignition\data`
   - a tag-type-definition tree with 156 files and 85 dirs

   File sizes may be small where content is not read. Use generic names only, with no site names.
2. **Offline test** through the sftp/winps test doubles. Listing the prod-shape tree must use at most a small constant number of ssh/sftp sessions. Assert the count with the existing `sessions` counter or an equivalent. It must return every entry identically to the reference walk. This test must FAIL on current main (RED first).
3. **Local conformance test** in the style of `deploy_host_conformance.rs`, against a real filesystem on macOS/Linux CI. Run a full read of the prod-shape tree at prod scale and assert a wall-clock budget. Pick a defensible number and justify it in a comment.
4. **Live test against the Windows test VM** (ign-win-836):
   - Its IP changes on every start, so `IGN_WINVM_HOST` in the env file may be stale. Find the current IP and export it in the shell. Never edit the user's env file.
   - Back up the VM's existing core tag folders first.
   - Seed a prod-shape tree into the test gateway's core tag folders. This is a test host.
   - Time `ign deploy verify` and `ign deploy plan` before and after the fix, and assert a full read finishes in under 2 minutes.
   - Restore the VM's original folders exactly, and verify the restore by hash or count.
   - Record the before and after times in SUMMARY.

   If the VM cannot be reached or the live rig cannot run, say so in SUMMARY. Do not fake the result.
5. **Test docs.** Add a short note wherever the existing test and rig docs live. It says the prod-scale fixture is the gate for deploy transport changes.
