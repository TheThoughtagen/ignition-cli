**Gathered:** 2026-10-29

<domain>
## Task Boundary

Make `ign deploy pull` and `ign deploy plan` usable against the production pair (WIGNVM01/WIGNVM04, Ignition 8.3.6, Windows, Win32-OpenSSH 8.1 sftp), released as v1.6.1.

Live evidence (2026-10-29): `ign deploy pull --env production` walked `core` for 53 minutes and then failed with `transport_failed` (exit 4):
`config/resources/core/ignition/tag-definition/MQTT Engine/Edge Nodes/wh_whk01_distillery01/Processing01/DistillateProcessing01/Control/TankState/CisternTank03/Schedule_Order_Data/tags.json has a path of 240 characters on the host; the sftp server cannot resolve paths of 260 characters or more`.
The `MQTT Engine` tag provider is generated by Cirrus Link from Sparkplug births. The gateway owns it and nothing ever declares it. It is the cause of both the slow walk and the failure.

Out of scope: upgrading OpenSSH on the hosts, a Cargo.toml version bump (release.yml stamps the version from the tag), and any change to the frozen envelope shape beyond additive keys.

<decisions>
## Implementation Decisions

### Where the exclusion list lives (user: "Both")
- Two sources:
  - **Target:** `targets/<env>.yaml` gets an optional top-level `exclude_tag_providers: [<provider name>, ...]`. This is what makes a bootstrap pull work, because there is no manifest yet at that point.
  - **Manifest:** `gateways/<name>/manifest.yaml` gets the same optional field. It belongs to the declared tree and applies to every environment.
- **Effective set:** the union of the built-in default (below), the target's list and the manifest's list.
- Parsing stays strict: unknown fields are still refused, an empty or blank entry is refused, and a duplicate is refused or normalized (planner decides, and states which).
- **Contradictions are refused:** a provider that is both excluded and declared (in the manifest's `tag_providers`, or present under `tags/` in the tree) is refused with `deploy_tree_invalid` (exit 2).
- **What exclusion means:** the provider's `ignition/tag-definition/<provider>/` subtree, plus any other per-provider tag type directories (planner checks the four tag types from the pull manifest docs), is never walked or read. That applies in `pull`, `plan`, `verify` and `apply`, including apply's live reads, snapshot and delete set. It is also never written and never deleted.
- **Excluded providers are reported, not silent:** an additive `data` key (for example `excluded_tag_providers`) in pull, plan, verify and apply output, plus a human-mode stderr line.

### Over-limit live paths that are not excluded (user: "Report, refuse if it matters")
- **pull:** skips the unit with a new reason, `path_too_long`, and adds it to the skip-reason table. The bootstrap continues.
- **plan:** lists the unit as `unreadable`, in a new list or relation the planner names. It is never treated as absent and never enters the delete set. `has_changes` and `plan_sha256` must cover it, so that a plan with unreadable units can't be mistaken for an identical plan without them.
- **apply:** refuses before any write when an unreadable unit is declared (rendered) or is in the delete set: the planner picks an existing exit-6 slug or adds one under the four-place rule. Otherwise apply proceeds and reports a warning.
- **verify:** a declared unit that is unreadable is a red finding. An unreadable unit that isn't declared is a warning.
- **Never** treat an unreadable unit as absent anywhere (spec: "Nothing was read as absent").

### Default exclusion (user: "Exclude System by default")
- `System` is always excluded, without being listed. The output still names it among the excluded providers.
- The planner must decide, and document, whether a target or manifest can turn the default off. The recommendation is no, since `System` is gateway-owned, but the planner may add an explicit opt-in if a real case needs `System` declared.

### Claude's Discretion
- Exact field names (`exclude_tag_providers`), the slug names, and the name of the plan relation or list for unreadable units.
- How the reader detects over-limit paths. It already refuses them with a message; ideally it detects them while listing, before trying to read.
- Whether the Linux transport and the local transport also apply the path limit. Only the Windows sftp server has the 260 limit; keep each transport's behaviour correct for that transport.

</decisions>
