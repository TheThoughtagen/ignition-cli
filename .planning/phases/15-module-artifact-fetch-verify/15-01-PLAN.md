<objective>
Build `ignition-core::module` — the library API that obtains a pinned, signed `.modl` release artifact from `WhiskeyHouse/ignition-git-module` and proves it is the right bytes before anything is allowed to depend on it. Lead with one production-quality end-to-end slice, then expand to the cache-authority and loud-refusal behaviors.

Purpose: this is `ign`'s first dependency on a third-party artifact feed. Phase 16 mounts these bytes into a live gateway; if the fetch/verify contract is wrong, that failure surfaces buried inside a Docker flow. Isolating it here makes every failure mode visible and testable.
Output: `crates/ignition-core/src/module/` (registry seam + fetch/verify), four new `CoreError` variants at existing exit codes, and a wiremock contract test binary covering SC-1, SC-3, SC-4.
</objective>

<phase_success_criteria>
The four criteria below are copied VERBATIM from `.planning/ROADMAP.md` → Phase 15. They are the spec; every task traces to one.

1. Given a pinned module version, `ign` resolves that release's signed `.modl` asset and downloads it; an unknown version fails loudly naming the version and the resolved URL, never falling back to "latest"
2. A downloaded artifact whose sha256 does not match the release's published digest is REFUSED — the bytes are discarded, nothing is cached, and the error names both expected and actual digests. This is a hard failure, never a warning
3. A verified artifact is cached keyed by version+digest; a second fetch of the same version reuses the cache and makes no network request (provable by a test that fails if a request is issued)
4. With a populated cache and no network, provisioning proceeds to completion — offline is a supported state, not a degraded one

Closed by: **SC-1** → this plan, Task 1 (resolve + download) and Task 3 (`unknown_version_names_version_and_url`, `missing_asset_names_expected_and_present`). **SC-2** → plan 15-02, Task 1. **SC-3** → this plan, Task 2 (`second_fetch_makes_no_network_request`). **SC-4** → this plan, Task 2 (`offline_with_populated_cache_succeeds` plus its negative half).

**Decisions carried in from the user — NOT open for re-litigation:**

- **D-01 — Library-only.** No clap subcommand, no CLI surface, no TUI surface in Phase 15. The deliverable is an `ignition-core` API proven by `cargo test`. CLI wiring is Phase 16 (RMOD-01).
- **D-02 — Digest-change policy.** A pinned version re-released upstream with different bytes is REFUSED by default, naming both the cached/expected digest and the new upstream digest, leaving the cached artifact intact — with a documented explicit override to deliberately accept the new bytes. Implemented in plan 15-02 via `FetchPolicy` (D-09); the enum is DEFINED here so no signature churn lands later.
- **D-03 — Separate HTTP client.** Build a fresh `reqwest::Client` for the artifact feed. Do NOT reuse `ReqwestGatewayApi`; do NOT copy the gateway client's redirect suppression (`crates/ignition-core/src/client/mod.rs:913-928`), which exists for the uncommissioned-gateway wizard 302 and would turn the mandatory release-CDN 302 into an unclassified response. Leave reqwest's redirect policy untouched (its default follows up to 10 hops). Both clients must still call `ignition_core::client::install_crypto_provider()` before their first request — the workspace builds reqwest with `rustls-no-provider` and a raw client panics on first TLS handshake without it.
- **D-04 — No new crates.** `sha2` is promoted from `ignition-cli`'s `[dev-dependencies]` into `ignition-core`'s `[dependencies]`, mirroring the `tempfile` precedent and its comment style at `crates/ignition-core/Cargo.toml:28`. `reqwest` (stream feature), `tempfile`, `directories`, `futures-util`, `thiserror` are already `ignition-core` production deps.

**Planner decisions made for this phase (the open questions the research left open):**

- **D-05 — Error variant names and slugs.** Four variants land in this plan, a fifth in 15-02. Every one is at an EXISTING exit code — same exit class, own slug, never a new exit code:

  | Variant | Slug | Exit | Raised when |
  |---|---|---|---|
  | `ModuleFeedUnreachable` | `module_feed_unreachable` | 4 | Transport failure reaching the feed or the asset CDN (DNS, connect, timeout, TLS) — the offline signal |
  | `ModuleFeedUnusable` | `module_feed_unusable` | 6 | The feed ANSWERED but not usably: 403 rate-limited, 401, 5xx, unparseable body, asset published with no sha256 digest, or a body exceeding the published size |
  | `ModuleReleaseNotFound` | `module_release_not_found` | 6 | No release exists for the pinned tag, or the release carries no asset of the expected name |
  | `ModuleDigestMismatch` | `module_digest_mismatch` | 6 | Downloaded bytes hash to something other than the release's published digest — SC-2's hard refusal |
  | `ModuleDigestChanged` (15-02) | `module_digest_changed` | 6 | Upstream now publishes a different digest for an already-cached version — D-02's refusal |

- **D-06 — A narrow network variant instead of reusing `CoreError::Network`.** `Network`'s `Display` hard-codes `"gateway unreachable at {url}"` (`crates/ignition-core/src/error.rs:181-193`). An offline module fetch would print "gateway unreachable at https://api.github.com/…" — actively wrong on two counts: `api.github.com` is not a gateway, and the user's actual gateway may be perfectly reachable. The taxonomy's own precedent is *accurate wording at an existing exit code* (`import_denied`, `bundle_not_available`, `node_tool_absent` all exist for exactly that reason). `ModuleFeedUnreachable` stays at exit 4, so the network exit class is unchanged; only the message is honest.
- **D-07 — Async-write bridge.** `tempfile::NamedTempFile::new_in(<module cache dir>)`, then `tokio::fs::File::from_std(temp.reopen()?)` for the async chunk writes, then `temp.persist(final_path)` after the digest check. Chosen over `spawn_blocking`-per-chunk (≈1000 task hops for a 7.7 MB artifact) and over a hand-rolled temp path + `tokio::fs::rename` (loses RAII cleanup). The `NamedTempFile` RAII drop IS the SC-2 mechanism: an early return discards the bytes structurally, not because some cleanup branch remembered to. If `reopen()` proves problematic on a platform, the fallback is `spawn_blocking` — never a direct write at the final path, which would reintroduce Pitfall 3.
- **D-08 — Cache layout.** `<cache_root>/modules/<module_id>/<version>-<sha256hex>.modl`, with the FULL 64-char lowercase hex digest in the filename (not a 12-char prefix) so the cache is self-describing and 15-02's drift refusal can name the cached digest in full with no sidecar index. `cache_root()` honors an `IGNITION_CLI_CACHE` env override first, then `directories::ProjectDirs::from("", "", "ignition-cli").cache_dir()` — exactly the `IGNITION_CLI_CONFIG` / `config_path()` shape at `crates/ignition-core/src/config/mod.rs:35-43`. The env override is what lets tests use a `tempfile::TempDir` instead of the developer's real cache. **Cache lookup is keyed by VERSION alone** — a hit must never require the feed, or SC-3 and SC-4 are impossible.
- **D-09 — `FetchPolicy` is D-02's override surface.** `CacheFirst` (default) / `Refresh` / `AcceptUpstreamChange`. All three behave IDENTICALLY on a cache miss — they differ only on a hit — so this plan implements the miss path once and 15-02 differentiates the hit path without changing a signature. Phase 16 wires `Refresh` and `AcceptUpstreamChange` to flags; that flag naming is Phase 16's, not this phase's.
