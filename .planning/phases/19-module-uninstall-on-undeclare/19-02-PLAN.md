<objective>
Make an undeclared module VISIBLE. `ign rig up` diffs what `ign` provisioned last
time against what the rig declares now and reports the difference as data — and
writes nothing to the gateway.

Purpose: a user who deletes a `[rigs.dev.modules.git]` table gets told the module
is still installed on the gateway and told which command removes it. Today they
get silence and a gateway that still reports the module healthy.

Output: a pure, exhaustively-tested diff in `rig::modules`, an additive
`orphaned_modules` key on both rig result shapes, and two independent proofs that
`rig up` never issues an uninstall.
</objective>

<design_decision>
## D-19-01 is settled in 19-01 and is binding here

`rig up` REPORTS; it never removes. The full rationale (four reasons, and the
rejected alternative) is recorded in `19-01-PLAN.md`'s `<design_decision>`
section. The two that constrain THIS plan:

- `IGNITION_YES=1` is a documented, encouraged pattern for agents and CI, and
  `apply_env_defaults` merges it into the global `--yes`. An inline uninstall
  would fire with no deliberation for exactly the users least able to notice.
- `rig up` runs with NO gateway credential today (the commissioned wait uses a
  header-less client against `/StatusPing` on purpose). Adding a gateway write
  would change `rig up`'s credential contract for every user.

## D-19-06 — the orphan set comes from the override file, nothing else

Three candidate sources were available; two are wrong.

- **The gateway's `/modules/healthy` list** would let `ign` "discover" modules it
  never provisioned — the precise over-reach SC-4 forbids — and would require a
  credential on `rig up` (see above).
- **The running container's mounts** are already known to go stale
  (19-RESEARCH Pitfall 3, live-verified): `existing_override`'s own doc comment
  claimed the file never accumulates stale state and was wrong.
- **The PRE-overwrite override file** is the one artifact `ign` wrote itself, on
  this disk, for this rig. It is read BEFORE anything rewrites or deletes it.

This is only trustworthy because the prerequisite landed: commit `50cfbbc`
("make D-08's override delete actually reachable") makes the file get cleaned up
on the real undeclare path via `clear_override`, called from both
`provision_modules`' early return and `main.rs`'s empty-merged-modules branch.
Without that fix, a stale override would make every subsequent orphan diff a lie.
**Do NOT re-plan that fix.** Verify it is present on the branch before starting.

## D-19-07 — registry intersection is SC-4's second belt

The parse maps each mount target back through `spec_for(id)` and DROPS anything
the registry does not know. A hand-edited override, a module from a future
`ign` version, or an id an operator typed by hand cannot become an orphan report.
Combined with 19-01's D-19-05 (the uninstall verb only accepts registry ids),
there are now two independent structural reasons a module `ign` did not provision
can never be removed by `ign`.
</design_decision>

| Boundary | Description |

| `ign` -> rig gateway | crossed by `rig up` for the header-less `/StatusPing` wait ONLY — no authenticated call, no write |
