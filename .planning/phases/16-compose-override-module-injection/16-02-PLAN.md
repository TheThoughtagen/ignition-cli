**Inherited verbatim from plan 16-01 — D-01 through D-14 apply unchanged.** In particular D-02 (the second module's identity), D-03 (`gateway_module_id` is its own field), D-04 (the `0600` fix is merged; do not re-plan it) and D-13 (one new slug only, `module_not_registered`, exit 3).

**Additional decisions for the CLI surface:**

- **D-15 — `--with-module ID@VERSION`, repeatable, on `Up` and `Reset`.** `Reset` gets it too because `rig_reset` runs the same `up_args` path internally. The `@` separator is unambiguous: `validate_module_id` allows `[a-z0-9-]` and `validate_version` allows `[A-Za-z0-9._+-]`, and neither includes `@`. Parsing is one `split_once`, and both halves go through the EXISTING validators — no third validator is written.
- **D-16 — The flag MERGES with config, winning per id.** `--with-module` does not replace the config's declarations; it adds to them, and a flag entry for an id the config already declares overrides that id's version for this invocation only. Rationale: a rig that declares the Git module and wants one extra module for a single run is the realistic case, and a bare rig with no config still gets a one-off module. A subtractive form (running WITHOUT a config-declared module) is deliberately out of scope for this phase — note it in the flag's help text so the behavior is discoverable, and do not invent one.
- **D-17 — Fetch-policy flags, closing Phase 15's explicit handoff.** `15-02-SUMMARY.md` records `FetchPolicy` as fully implemented and deferred to Phase 16 for CLI wiring. Expose exactly two flags on `Up` and `Reset`: one that re-verifies cached versions against the feed (`Refresh`), and one that accepts a changed upstream digest (`AcceptUpstreamChange`). Default stays `CacheFirst`. The accept flag must be its own explicit flag, never implied by the refresh flag — D-02 of Phase 15 made accepting a re-released artifact a deliberate act, and collapsing the two would silently undo that.
- **D-18 — `--with-module` is NOT a guarded operation.** It provisions a module onto a rig the user is already bringing up; `rig up` is not in `GUARDED_OPS` today and this flag does not make it destructive. `rig reset` remains guarded for the reason it already is (volume teardown), unchanged.
- **D-19 — No new exit-code slug in this plan.** Malformed flag values land on the existing `invalid_input` (exit 2) via the existing validators; an unregistered id lands on `module_not_registered` (exit 3) introduced in 16-01. `README.md`'s exit table needs no further change.

**Test-matrix rule (inherited, MANDATORY):** every behavior this plan changes must be tested against PRE-EXISTING on-disk state as well as fresh state. Concretely here: a rig whose override was written by a previous run at ONE module and is now invoked with a second module added, and a cache that already holds one of the two artifacts while the other must be fetched.

**Environmental lock:** no git worktree for this phase (`.claude/CLAUDE.md` → "Worktrees and cargo builds"). Also note the standing rule in `.planning/STATE.md`: after any transport- or CLI-affecting change, `cargo install --path crates/ignition-cli --force` is REQUIRED before any manual smoke check — `ign` on PATH is the installed binary, not the repo build.
