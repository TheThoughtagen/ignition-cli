<objective>
Build the mechanism that makes a declared module actually reach a rig's gateway: a generated, `ign`-owned `compose.ign-modules.yml` carrying a read-only bind mount of the Phase 15 cached artifact plus the gateway's acceptance variables, passed as a second `-f` to the existing compose invocations.

Purpose: Phase 15 proved `ign` can obtain the right bytes. Those bytes are inert until a rig boots with them mounted. This plan is where the phase's architectural risk lives — compose merge semantics, `-f` ordering, and the three ways a bind mount can silently do nothing.
Output: `crates/ignition-core/src/rig/modules.rs`, the config surface (`[rigs.NAME.modules.*]`), one new error variant at an existing exit code, and a contract-test binary whose goldens pin the generated bytes.
</objective>

<phase_success_criteria>
Copied VERBATIM from `.planning/ROADMAP.md` → Phase 16. They are the spec; every task traces to one.

1. A rig with no module declaration behaves byte-identically to today — no override generated, no env vars added, no behavior change (regression-proven against existing rig tests)
2. A rig with a declared module comes up with that module LOADED and running on a stock `inductiveautomation/ignition` image — no custom image, no developer mode, verified on a live rig
3. The module survives `ign rig down` followed by `ign rig up` — the mount is declared in the override, not copied into a container (the recreate is the test)
4. `ign` never writes to the user's compose file; the override is a separate `ign`-owned file carrying a generated-by header, and deleting it fully reverts provisioning
5. A second, different module registers and provisions through the same seam with no Git-module-specific code path — the registry abstraction is proven, not asserted

Closed by: **SC-1** → this plan, Task 1 (`up_args_pinned` unchanged) and Task 3 (`down/ps/logs` pinned + the undeclare-reverts test). **SC-4** → this plan, Task 1 (header + `user_compose_file_is_never_modified`) and Task 2 (delete-on-undeclare). **SC-3's mechanism half** → this plan, Task 3 (the same override `-f` in both the down and the following up call sequence); SC-3's live half → plan 16-03. **SC-2** → plan 16-03. **SC-5** → plan 16-02 (registration) and 16-03 (live proof).

**Planner decisions closing the remaining open questions:**

- **D-05 — "Module loaded" is proven by the gateway's own module list.** 16-RESEARCH.md Open Question 3 is closed WITHOUT new API surface: `GatewayApi::modules(quarantined, &ListQuery)` already exists (`crates/ignition-core/src/client/mod.rs:106-112`), backed by `/data/api/v1/modules/healthy` and `/data/api/v1/modules/quarantined` (`crates/ignition-core/src/client/status.rs:32-35`), returning `ModuleInfo { id, name, version, state, .. }`, already surfaced as `ign gateway modules [--quarantined]`. The live proof is: the module's `gateway_module_id` appears in the HEALTHY list and does NOT appear in the QUARANTINED list. Plan 16-03 owns that test; this plan adds nothing to the client layer.
- **D-06 — Hand-rolled override writer, no YAML crate.** No actively maintained serde-derive YAML crate exists (16-RESEARCH.md Package Legitimacy Audit: the incumbent is self-deprecated, its most visible fork is ~21 months stale, and the maintained emitters have no derive story). This is GENERATION of a six-key, fully-controlled subset from already-charset-validated inputs — not parsing of hostile data — and matches the hand-rolled-TOML precedent in `.claude/CLAUDE.md` §8. `Cargo.lock` must not change.
- **D-07 — Long (mapping) volume syntax, single-quoted paths.** Every volume entry is emitted with explicit `type`, `source`, `target` and `read_only` keys. The short colon-separated form is never emitted: its separator collides with a Windows drive letter and CI's matrix includes `windows-latest`. Paths are emitted as SINGLE-quoted YAML scalars (escape an embedded apostrophe by doubling it), never double-quoted: in double-quoted YAML a backslash is an escape character, so a Windows path would be mangled a second way. Environment VALUES are double-quoted — `Y` unquoted is a YAML boolean.
- **D-08 — Tri-state override lifecycle.** Modules declared → write (overwrite whole); none declared → `remove_file`, tolerating `NotFound`; and the `-f` is passed only for a file `ign` confirmed it wrote or found this run. Never an empty-but-present file (research Pitfall 4).
- **D-09 — The resolve step does NOT receive the override.** `config_args` stays exactly as it is. The resolved config is the truth about the USER's rig — its identity, services, ports and volumes feed `rig status`, the port pre-flight and the gateway-URL heuristic, and `ign`'s own injected mount must never appear there. Ordering follows: resolve first (no override), then provision, then act.
- **D-10 — Override path and file name.** `compose.ign-modules.yml`, always at `std::path::absolute(plan.project_dir.join(OVERRIDE_FILENAME))`. Absolute unconditionally, because `DockerCompose::spawn` does not set `current_dir` and a `[rigs.NAME]` `compose_file` is not canonicalized (research Pitfall 7). Use `std::path::absolute` (stable 1.79, under the 1.85 MSRV), NOT `canonicalize` — the latter resolves symlinks and would rewrite paths the user recognizes.
- **D-11 — `-f` order is enforced in ONE helper.** A single private helper in `rig/compose.rs` pushes `-p <name>`, `-f <base>`, then `-f <override>` for each override, used by `up_args`, `down_args`, `ps_args` and `logs_args`. Four independent implementations would drift, and an override that landed FIRST would invert merge precedence and move `--project-directory` inference (research Pitfall 3).
- **D-12 — The target service is derived, with an escape hatch.** `parse_config` gains `gateway_service: Option<String>` on `RigPlan`: the first service (services arrive in sorted key order — `serde_json` is built without `preserve_order`, so its map is ordered) that publishes a port whose target is `GATEWAY_HTTP_TARGET`, else `GATEWAY_HTTPS_TARGET` — the same documented heuristic `gateway_url_from` already uses, one layer down. `RigEntry.module_service` overrides it. Modules declared with neither available is a refusal naming `plan.services` and the override key, never a guess at a service name.
- **D-13 — One new error variant, at an existing exit code.** `ModuleNotRegistered { id: String, known: Vec<String> }`, exit 3, slug `module_not_registered` — structurally the `ProfileNotFound { name, known }` shape (`crates/ignition-core/src/error.rs:133`), which is exit 3. A well-formed id that is simply not registered is a CONFIG problem, not malformed input (exit 2 belongs to `validate_module_id`/`validate_version`) and not a Docker failure (exit 7). Every pre-flight refusal — missing artifact, non-file artifact, relative path, underivable service — is `CoreError::Rig` (exit 7, existing `rig_error`), per the design doc's "Docker/compose failures surface through the existing rig error class". This is the phase's ONLY new slug; the Three-Place rule (variant + `EXIT_SLUG_LITERALS` + README) is machine-checked by `readme_exit_table_agreement`.
- **D-14 — Provisioning is a core function, not dispatch logic.** `provision_modules` in `rig/modules.rs` owns: registry lookup, fetch through Phase 15's `ModuleFeed`, pre-flight, generate, write-or-delete. It returns a `ModuleProvisioning` that carries the override path (or `None`) and the per-module outcome. `rig_up`/`rig_reset` take that value; they never fetch. This keeps the whole mechanism testable with a wiremock feed and a `TempDir`, with no Docker and no CLI.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| config TOML / one-off flag → generated YAML | Module ids and version strings are user-controlled text that becomes a filesystem path, a YAML scalar and a process argument. |
| `ign` → the rig's project directory | `ign` writes a new file into a directory the user owns, next to a file `ign` must never modify. |
| cached `.modl` on the host → the gateway container | An artifact path crosses into a container's module-scan directory as a bind mount. |
| generated override → `docker compose` | The override's content becomes part of the resolved service definition for a process running with the user's Docker access. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-16-01 | Tampering | `generate_override` value interpolation | high | mitigate | Every interpolated value is either charset-validated by Phase 15's `validate_module_id`/`validate_version` (reused, never re-derived) or a path `ign` itself constructed. Paths are single-quoted YAML scalars with apostrophe doubling (D-07), so no value can terminate its scalar and inject a sibling key. Task 1 golden tests pin the exact bytes; Task 2 proves the refusals fire before generation. |
| T-16-02 | Spoofing | the bind-mount source path | high | mitigate | A missing bind source becomes a silently empty DIRECTORY on host and container (reproduced live in 16-RESEARCH.md), leaving a rig that boots healthy with no module. | T-16-03 | Tampering | the user's compose file | high | mitigate | `ign` writes only `compose.ign-modules.yml` and only within `plan.project_dir`.
