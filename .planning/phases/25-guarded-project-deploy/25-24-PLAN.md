<objective>
Close G-25-11: a check token minted for a read-only level must not be able to write.

Today the permissions step of `ign adopt` calls `merge_level_into` on both readPermissions and writePermissions. That function adds the bare root of the granted level. For the default `Authenticated/Roles/Administrator`, the root is `Authenticated`, and every API key is Authenticated, so after one adopt any key on the gateway passes the write check. In the UAT, a key granted only a CIRead level answered 200 on a write probe. The deploy workflow's secret split rests on the check token being read-only, because the check job runs before any reviewer approves.

The fix cannot simply write the nested level instead. `.planning/research/ADOPT-RESEARCH.md` pitfall 3 recorded on 8.3.6 that a nested `Authenticated>Roles>Administrator` write entry did NOT admit a token granted exactly that path, which is why adopt adds the bare root. So this plan first captures, on fresh gateways, which entry forms admit which keys. It then implements the write scope the capture's decision allows: the exact level when nested entries work, otherwise a dedicated write level. It adds `--read-only` (a key that is proven refused write) and `--restrict-write` (an explicit removal of the bare Authenticated entry that earlier adopts left on a gateway). It documents how to mint and verify a read-only check token.

Purpose: DPRJ-05's `--check` "with no writes" is enforced by the gateway, not only by the CLI, once the check token cannot write.
Output: the capture (live test, fixture, recorded matrix and decision), the adopt changes with offline tests, the live end-to-end test, the CLI contract test and the README adopt section.
</objective>

## Decisions carried into this plan

- **Capture first.** Whether a nested writePermissions entry admits a token is not known for the target versions. ADOPT-RESEARCH pitfall 3 says it did not on 8.3.6, both with and without descriptions. Whether a dedicated level that no security-level definition declares works as a key grant is not known either. The plan does not guess: Task 1 measures both on the two image tags the repo already uses, and Task 2 implements only what the measured decision allows.
- **Decision rule** (pure `decide`, tested offline, applied in this order):
  - `nested-exact` when, in state S1 (writePermissions = the commissioned list only), the Administrator key writes and the IgnCapRead key is refused.
  - else `dedicated-nested` when, in S3 (commissioned + nested `Authenticated>IgnCapWrite`), both keys holding `Authenticated/IgnCapWrite` write, and the Administrator-only and IgnCapRead keys are refused.
  - else `dedicated-root` when, in S2 (commissioned + bare `IgnCapWrite`), both keys holding `IgnCapWrite` write, the Administrator-only and IgnCapRead keys are refused, and the Administrator+IgnCapWrite key still reads.
  - else `none`.

  `nested-exact` is preferred because it adds no level to anyone's key. Between the dedicated forms, the one under `Authenticated` is preferred because it adds no root-level name to the gateway's level tree.
- **Default write level per decision.** `nested-exact` gives the key's own `--level` (the default adopt then grants exactly what it grants today, and writes only through that level). `dedicated-nested` gives `Authenticated/IgnCliWrite`. `dedicated-root` gives `IgnCliWrite`. Under a dedicated decision the minted key also gets that level. A key minted by an earlier release does not hold it, so the existing-key check refuses it with the existing "exists at level ... requested" message, and the operator deletes the key and re-runs. This is recorded as a costly behaviour change.
- **Removal is opt-in.** Gateways adopted by earlier releases hold a bare `Authenticated` write entry that other integrations' keys may rely on. Adopt reports it (warn) and removes it only with `--restrict-write`. The removal is reversible (re-add the entry in Platform > Security > General Settings > Gateway Write Permissions), so it is rated costly, not one-way.
- **The probe writes.** The default adopt's probe now also runs the harmless scan/projects rescan, the same probe as doctor's `--check-write`, so a key that cannot write is caught at adopt time instead of at the first deploy.
