`rig_logs` differs from every prior action: output is a raw stream, not an ActionOutput.

**`actions::rig::rig_logs(runner, plan, tail: u32, follow: bool, service: Option<&str>, sink: &mut dyn FnMut(String) -> ())`** — the actions::logs tail-loop precedent (printer-free via a sink; main.rs owns the actual printing):
- One-shot (no follow): run `logs_args(tail, false, service)`, split stdout lines → sink each
- Follow: spawn via the runner with streamed stdout (`tokio::process` with piped stdout, forward lines to sink until EOF/child-exit; Ctrl-C = default process kill, README-documented like `logs -f`)
- stderr passthrough decision: compose diagnostics go to OUR stderr (tracing::warn), never the data sink
- Under `--json` non-follow: lines stay RAW (compose log lines are not gateway JSON objects; wrapping would corrupt them) — `rig logs --json` = same passthrough. The streaming-exception README entry covers both modes. No NDJSON transformation attempted (contrast: `logs -f --json` streams gateway NDJSON because entries ARE JSON objects).

Unit tests: fake runner returning multi-line stdout → sink receives lines verbatim; follow-mode fn signature compiles against the seam (fake runner implements streaming via a channel or preloaded pipe — keep the fake simple: preload).
