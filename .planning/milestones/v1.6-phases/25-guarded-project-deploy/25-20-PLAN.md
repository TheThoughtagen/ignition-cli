<objective>
Close G-25-4: on a Windows ssh gateway host the release-record replace is `Move-Item -Force`, which on Windows PowerShell 5.1 is delete-then-rename, so a concurrent reader saw `release.json` missing (measured live 2026-10-26 on ign-win-836: 0 torn but 175/55 of ~17k local reads and 1/381 sftp reads missing). `read_release_record` maps a missing file to `Ok(None)`, which `deploy_projects_prepare` reads as "never deployed here" and the children sweep as `Unverified` — a concurrent read during a write can decide on the wrong state.

Replace the Windows record replace with a single atomic rename-with-replace (Win32 `MoveFileEx` `MOVEFILE_REPLACE_EXISTING | MOVEFILE_WRITE_THROUGH` via Add-Type P/Invoke), fail closed when the P/Invoke cannot run, keep the WR-04 bounded-retry-then-clean-error behaviour, and prove it with a concurrent-reader race sized against the UAT run: a negative control on the old script must show missing reads, and the shipped script must show 0 torn and 0 missing while meeting stated floors for successful replaces, read volume and distinct versions seen.

Purpose: a reader on a Windows host must see the old record or the new one, never a missing or torn file (DPRJ-03, D-03/D-06/D-12 all read the record).
Output: the atomic Windows record-replace script and its guard, the rewired `replace_record`, updated unit/mock tests, the live preflight, negative control and race gate on ign-win-836, and docs/captures corrected for the Windows claim.
</objective>

## Decisions carried into this plan

- Mechanism: MoveFileEx(MOVEFILE_REPLACE_EXISTING | MOVEFILE_WRITE_THROUGH), fixed by this plan. A live failure stops the checkpoint and becomes a new gap; no other mechanism is implemented inside this plan.
- Reader side (item 3): no reader retry in this plan (it would slow the legitimate "no record yet" read and only make a wrong answer rarer). A scoped `read_release_record` re-list is the documented follow-up if the gate ever shows a missing read with MoveFileEx.
- The gate cannot pass vacuously: a negative control on `MOVE_REPLACE` must show missing reads, and the shipped run must meet floors for successful replaces, read volume and distinct versions seen, with torn judged by exact length plus matching head/tail versions.
- Floor calibration: a 20 s calibration run sets the expectation (500 to 3,000 replaces in 120 s) and picks the constants. A throughput-only miss (0 torn, 0 missing, 0 backwards) gets one rerun at the fallback constants fixed in this plan (300 s, 30 ms reader cadence), and a second throughput miss is reported as a gate-throughput gap, never as a failed fix. Any torn, missing or backwards read is a failed fix at once, with no retry.
- `RECORD_REPLACE` compiles its P/Invoke type only when `IgnRecord.Native` is not loaded yet. This matters only to the in-process harness loop; production runs one fresh process per replace.
- No new CoreError slug: a blocked or impossible atomic replace stays `transport_failed` (exit 4); the post-import record-write failure stays `record_written:false` + warning (existing WR-04/WR-05 behaviour).
- Scope is the Windows release-record replace only. Linux `mv -f --` and the apply mirror move in `scripts/commit.ps1` are untouched.
