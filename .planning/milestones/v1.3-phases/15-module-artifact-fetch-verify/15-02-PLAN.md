<objective>
Close the integrity half of the phase: bytes that are not the right bytes are refused loudly and leave nothing behind, and a pinned version whose upstream bytes changed under it is refused by default with an explicit, documented way to accept the change.

Purpose: SC-2 is the reason this phase exists — everything Phase 16 mounts into a gateway rests on "these bytes were proven". A verification that warns, or that leaves a partial file where a later cache hit would find it, is worse than no verification at all.
Output: the digest-mismatch and published-size refusals, `FetchPolicy`'s hit-path behaviors with the fifth `CoreError` variant, and an opt-in live test proving the mocked feed shape matches the real one.
</objective>

<phase_success_criteria>
Copied VERBATIM from `.planning/ROADMAP.md` → Phase 15. This plan owns criterion 2 outright and re-guards 3 and 4 against the drift feature it adds.

1. Given a pinned module version, `ign` resolves that release's signed `.modl` asset and downloads it; an unknown version fails loudly naming the version and the resolved URL, never falling back to "latest"
2. A downloaded artifact whose sha256 does not match the release's published digest is REFUSED — the bytes are discarded, nothing is cached, and the error names both expected and actual digests. This is a hard failure, never a warning
3. A verified artifact is cached keyed by version+digest; a second fetch of the same version reuses the cache and makes no network request (provable by a test that fails if a request is issued)
4. With a populated cache and no network, provisioning proceeds to completion — offline is a supported state, not a degraded one

Closed by: **SC-2** → Task 1 (`digest_mismatch_refuses_and_caches_nothing`, `truncated_body_is_a_mismatch_not_a_cache_entry`, `mismatch_error_is_not_downgradable`). **SC-3 regression guard** → Task 2 (`cache_first_never_consults_the_feed_after_a_rerelease` — the drift feature must not have created a path that phones home for a cached version). **SC-1 / SC-4** → closed in plan 15-01 and re-proven against the real artifact by Task 3's opt-in live run.

<planner_locks>

Plan 15-01's `<planner_locks>` carry forward unchanged (D-01 library-only, D-02 digest-change policy, D-03 separate client, D-04 no new crates, D-05 through D-09, and the worktree/cargo-target-dir rule). The ones this plan acts on directly:

- **D-02 / D-09 — the two digest questions are NOT the same question, and only one of them is overridable.**

  | Question | When | Default | Override |
  |---|---|---|---|
  | *Do the bytes I just downloaded match the digest this response published?* | Every download | REFUSE (`module_digest_mismatch`) | **None, ever.** This is the integrity check itself; an override here would make the whole phase decorative. |
  | *Does the digest upstream publishes today differ from the one I cached for this version?* | Only on `Refresh` / `AcceptUpstreamChange` | REFUSE (`module_digest_changed`), cached artifact left intact | `FetchPolicy::AcceptUpstreamChange` — and the newly accepted bytes are STILL verified against the newly published digest before they are cached. |

  Conflating these is the failure mode to guard against. Task 2 must not route the mismatch path through any policy check.

- **D-05 — the fifth and final variant.** `ModuleDigestChanged { module, version, cached_digest, upstream_digest, cached_path }`, slug `module_digest_changed`, exit **6** (target state — the same class as the other module refusals, no new exit code). Its `Display` names both digests in full and the path of the cached artifact that was left untouched; its `hint()` names the override as the deliberate way forward.

- **Cache is never destructive.** No path in this phase deletes, overwrites or truncates an existing cache entry. `AcceptUpstreamChange` persists the new digest's file ALONGSIDE the old one (the filename differs by construction — D-08 puts the full digest in the name). Leaving the old entry is what makes the refusal recoverable: the user can still run offline on the bytes they already trusted.
</planner_locks>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| release CDN → local filesystem | The streamed body is fully attacker-controlled if the CDN or the path to it is compromised; it is the input to the only check standing between the feed and a file Phase 16 mounts into a gateway. |
| cached artifact → a later offline run | A cache entry is trusted without re-verification on every subsequent fetch, so whatever reached the cache is trusted indefinitely. |
| `api.github.com` release metadata → the drift decision | The published `digest` and `size` fields drive both the accept/refuse decision and the stream cap. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-15-08 | Tampering | streamed artifact body | critical | mitigate | Task 1: the sha256 over the streamed bytes must equal the published digest or the bytes are discarded and nothing is cached, under every `FetchPolicy` — `mismatch_error_is_not_downgradable` pins that no override exists. |
| T-15-09 | Tampering | partial / interrupted download | high | mitigate | Task 1: `truncated_body_is_a_mismatch_not_a_cache_entry` plus the `NamedTempFile`-then-persist ordering (D-07) mean a short body fails the digest check and its bytes are dropped; incomplete bytes cannot occupy the final path. |
| T-15-10 | Denial of Service | oversized / endless response body | medium | mitigate | Task 1: the running byte total is checked against the API-published `size` after each chunk and the stream is abandoned on exceeding it — `Content-Length` is explicitly not trusted in its place. |
| T-15-11 | Tampering (supply chain) | silent upstream re-release of a pinned version | high | mitigate | Task 2: on any refresh, a changed upstream digest is refused by default naming both digests (`module_digest_changed`), so a re-tagged release cannot slip new bytes under a pinned version. Accepting it requires an explicit, documented policy value. |
| T-15-12 | Tampering | destruction of a trusted cache entry | medium | mitigate | No code path in `module/` removes, truncates or overwrites a cache entry — enforced by the Task 2 structural gate. The override adds a file, never replaces one, so the previously trusted bytes remain available offline. |
| T-15-13 | Information Disclosure | the opt-in live test | low | accept | The live test fetches a public asset from a public repo unauthenticated; it sends no token and writes only into a temp dir. Gated behind `#[ignore]` + an env var so it never runs in CI. |

No legitimacy checkpoint is required. |
