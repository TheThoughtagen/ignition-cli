<objective>
Prove on a real gateway what the unit tests can only prove structurally: that a declared module is actually LOADED, that the acceptance variables clear commissioning without a human, that the module survives a full recreate, and that deleting the override reverts it.

Purpose: SC-2 and SC-3 are the criteria that cannot be faked. Every earlier test in this phase asserts on argument vectors and generated bytes; none of them can tell you whether Ignition's module scan accepted the mount. This plan is the falsification attempt.
Output: an `#[ignore]`-gated live test, a minimal stock-image fixture rig, and a recorded evidence file.
</objective>

1. A rig with no module declaration behaves byte-identically to today — no override generated, no env vars added, no behavior change (regression-proven against existing rig tests)
2. A rig with a declared module comes up with that module LOADED and running on a stock `inductiveautomation/ignition` image — no custom image, no developer mode, verified on a live rig

<planner_locks>

**Inherited verbatim from plans 16-01 and 16-02 — D-01 through D-19 apply unchanged.** D-05 in particular: the module-loaded proof uses the EXISTING `GatewayApi::modules` surface; this plan adds nothing to `crates/ignition-core/src/client/`.

**Additional decisions for the live gate:**

- **D-20 — Two-layer opt-in, matching `live_module_fetch.rs`.** Every test is `#[ignore]`-gated AND additionally gated on an explicit environment variable being set to `1`. A bare `cargo test -- --ignored` with the variable absent is a green no-op that prints a skip line, never a failure. CI never runs this and must never need Docker, a network or a gateway to stay green.
- **D-21 — The fixture rig sets NO acceptance variable.** `crates/ignition-core/tests/fixtures/live-rig/compose.yml` declares one service on a stock `inductiveautomation/ignition` image with a published gateway port, an admin username and an admin password, and nothing else. It deliberately omits the EULA, certificate and licence acceptance variables. This is the negative control that makes RMOD-05 falsifiable: if the override did not supply them, the gateway would sit at the commissioning wizard and `rig up`'s commissioned wait would return the uncommissioned-as-data state. A fixture that pre-accepted the EULA would make the test pass for the wrong reason.
- **D-22 — The gateway credential is basic auth from the fixture's own admin user.** `ReqwestGatewayApi::for_tests(&url, Some(Credential::Basic(..)))` with the username and password the fixture compose set, read from environment variables the test documents. No API-token generation flow is built for this test — that would add a commissioning dependency this phase does not own.
- **D-23 — The honest fallback, if the module list proves unusable.** If `GatewayApi::modules` cannot answer on a freshly commissioned rig (an auth or timing problem, not a design problem), the test must NOT be quietly weakened into an artifact-presence check and still called SC-2. Record the failure in `16-LIVE-GATE.md`, keep a clearly-named secondary assertion (the mounted path is a regular file inside the container and the gateway log names the module) as EXPLICITLY WEAKER evidence, and state plainly in the evidence file that SC-2 is partially proven. Do not claim a criterion is met by a check that cannot distinguish "loaded" from "mounted".
- **D-24 — The acceptance-variable list format is under test here.** Plan 16-02 comma-joins the gateway ids for a multi-module rig and marks it as an assumption. This run either confirms it or falsifies it. If the two-module rig commissions but only one module clears its certificate gate, the joining helper (a single named function per 16-02 Task 1) is corrected, the 16-02 golden is updated in the same commit, and the run is repeated. Correcting it is in scope for this plan; redesigning the override shape is not.
- **D-25 — Timings and versions are recorded, not remembered.** `16-LIVE-GATE.md` follows the `10-LIVE-GATE.md` precedent referenced in `.planning/STATE.md`: the exact image tag, the gateway version string the run observed, the module ids and versions observed in the healthy list, wall-clock durations for each `up`, and any deviation. A later phase debugging a commissioning problem needs the numbers, not a claim that it worked.

**Test-matrix rule (inherited, MANDATORY):** the live sequence must exercise PRE-EXISTING state, not only a fresh rig. Concretely: the second `up` in §B runs against an override file and a cache that both already exist, and §C runs against a rig directory that already holds a gateway data volume from the previous cycle.

**Environmental lock:** no git worktree (`.claude/CLAUDE.md`). Docker plus Compose v2 is required for this plan only; every other plan in this phase is Docker-free. `ign` on PATH is the installed binary — run `cargo install --path crates/ignition-cli --force` before any manual smoke check.

    - `rig down`, delete the override file by hand, `rig up` with NO declarations.

Structure the three tests as one ordered sequence sharing a setup helper rather than three independent rig lifecycles — bringing an Ignition gateway up three times from scratch is minutes of wall clock for no added signal, and §B's whole point is that it runs against §A's state. Rust test ordering is not guaranteed, so express the sequence as ONE `#[tokio::test]` whose body runs §A, §B and §C in order with clearly-labelled sections and assertions, plus a teardown that runs on every exit path. Build the gateway client per D-22 with basic auth from environment variables the module doc table documents, pointed at the URL derived from the rig plan by the existing `gateway_url_from` helper rather than a hardcoded port — the fixture's published port must be free to change without editing the test.

The module-list assertion is the heart of this plan. Assert on the gateway's OWN answer: fetch the healthy list, collect the ids, and assert set membership for each `gateway_module_id` read from the registry rather than from a literal — a literal here would pass even if the registry changed underneath. Fetch the quarantined list and assert non-membership. Include the full observed id list in the assertion message so a failure is diagnosable from the output alone without a second run.

Give the module-list fetch a short bounded retry: a gateway that just reported running may still be finishing its module scan. Bound it to a small number of attempts with a stated interval and fail with the last observed list rather than looping indefinitely. Do not conflate this with `rig up`'s commissioned wait, which is already done by the time this runs.

Teardown must be unconditional. A failed assertion that leaves a container and a volume behind will poison the next run and cost more time than the test saves.
