<objective>
Ship the deliberate, guarded gateway write: `ign rig module uninstall <ID> --yes`.

Purpose: Phase 16 shipped a false claim — deleting the override reverts the
mount, not the gateway's install. This plan builds the one thing that can make
the gateway forget, and builds it so it cannot report a success the gateway did
not perform.

Output: a new `GatewayApi` capability, a new typed denial error, a new guarded
CLI leaf, and a wiremock contract test that pins the request body and BOTH
response verdicts.
</objective>

<design_decision>
## D-19-01 — `rig up` REPORTS an orphan; a separate guarded verb removes it

**Settled here.** The ROADMAP left this open to the planner ("whether an
undeclared module is uninstalled at all as part of `rig up`, or whether `rig up`
merely REPORTS the orphaned module and removal is a deliberate verb"). The
answer is **report-only on `rig up`, plus `ign rig module uninstall <ID> --yes`.**

Four reasons, in order of force:

1. **`IGNITION_YES=1` makes a mid-`up` confirmation a no-op.** `--yes` is a
   GLOBAL arg and `apply_env_defaults` merges `IGNITION_YES` into it. An agent
   or CI job that exports `IGNITION_YES=1` (the documented, encouraged pattern
   for non-interactive use) would have `ign rig up` silently and irreversibly
   destroy a gateway module on the next TOML edit. A gate that the project's own
   recommended usage disables is not a gate.
2. **`GUARDED_OPS` cannot express a conditionally destructive verb.** The
   registry is a static `&[(&str, &str)]` keyed by clap leaf path, and `mcp.rs`
   reads it to synthesise the `confirm` property for every tool. A `rig up` that
   is destructive only when an orphan happens to exist would either advertise
   `confirm` always (wrong for the 99% case) or never (wrong for the dangerous
   case). The registry is the safety mechanism; a verb it cannot describe is a
   verb it cannot guard.
3. **`rig up` would newly require a gateway credential.** Today `rig up` runs
   with no credential at all — the commissioned wait uses a HEADER-LESS client
   against `/StatusPing` precisely so readiness never depends on auth. An inline
   uninstall needs an authenticated `/data/api/v1` call, which would either make
   `rig up` fail for every credential-less user or make the removal silently
   skip when no token is present. Both are worse than reporting.
4. **Irreversibility, and the repo's own convention.** Live fact 3: after a
   successful uninstall, re-declaring and re-mounting does NOT bring the module
   back — recovery today means `ign rig reset`, which destroys the rig's data
   volume. Every destructive verb in this codebase is a deliberate, separate
   command (`project delete`, `rig reset`, `rig restore`, `rig trial reset`),
   never a side effect of a routine one. Asking a user mid-`up` to approve an
   irreversible act they did not set out to perform is the shape that produces
   reflexive approval.

**Rejected alternative:** uninstall inline on `rig up` behind the confirmation.
Rejected on (1) and (2) — the gate would be structurally unrepresentable and
practically bypassed — with (3) and (4) as independent grounds.

**Consequence (binding on this plan and 19-02):** `rig up`/`rig reset` make ZERO
gateway writes. This plan builds the only write path; 19-02 builds the report.
</design_decision>

- **D-19-02 (user lock):** an uninstall REQUIRES confirmation. The uninstall
  path joins `GUARDED_OPS` and refuses without `--yes` (exit 2,
  `confirmation_required`), following the `project delete` precedent. **`rig up`
  itself stays UNGUARDED** — the gate belongs on the destructive act.
- **D-19-03 (live-verified):** `DELETE /data/api/v1/modules/uninstall` ALWAYS
  answers HTTP 200. Success rides the body: `{"success": bool,
  "failedUninstalls": {"uninstall": [ids]}}`. Parsing the status would report
  success on every failure. Follow the `CoreError::ImportDenied` precedent
  (05-07): a typed variant carrying the gateway's own refusal detail.
- **D-19-04 (live-verified gap):** batch atomicity for a MIXED success+failure
  batch was never observed (19-RESEARCH A2/Q1). Sidestep it: ONE call per module
  id, never a batch. The verb takes exactly one id.
- **D-19-05:** the verb accepts an `ign` REGISTRY id (`git`,
  `project-scan-endpoint`), never a raw gateway module id. `spec_for(id)` maps to
  `gateway_module_id`. This is SC-4's structural guarantee at the CLI surface: a
  hand-installed gateway module cannot be named at all, so it cannot be removed.
</locked_decisions>
