<design_decision>
## D-19-08 — the "module `ign` did not place" seed is the stock image's own modules

SC-4 says the test must "seed a gateway-installed module `ign` did not place."
The obvious reading — install a third module through some other mechanism — is
not available: `ign` has no install path other than the mount, and
`POST /data/api/v1/modules/install` was never probed (19-RESEARCH Q3, LOW
confidence, explicitly out of scope).

The stock `inductiveautomation/ignition` image ships with its own modules already
installed, and `ign` did not place a single one of them. They satisfy the
criterion's intent exactly and better than a synthetic seed would: they are real
gateway-installed modules, present for real reasons, and any over-reaching diff
or over-broad uninstall would take them.

The test therefore reads `/modules/healthy` BEFORE the uninstall, filters out
`ign`'s two registry gateway ids, and uses the remainder as the seed set. Two
assertions make it non-vacuous:

1. The seed set must be **non-empty**, or the test fails. A vacuous pass is the
   failure mode this whole plan exists to prevent.
2. The seed set must be **unchanged** after the uninstall, and no member of it
   may ever appear in `rig up`'s `orphaned_modules`.

Rejected alternative: hardcoding `com.inductiveautomation.reporting`. The
research's probe sent that id and got `success:false` — which is the SAME answer
a bogus id gets, so it is not evidence the module is installed. Reading the list
is evidence; a literal is a guess.

## D-19-09 — §C stops hand-deleting the override

§C currently does `std::fs::remove_file(&override_path).expect("delete override
by hand")` before bringing the rig up. That hand-deletion is what MASKED the dead
`write_override` delete branch for an entire phase: the test deleted the file, so
it never noticed that `rig up` did not. With `undeclared_provisioning` in place
(19-02), §C must let `rig up` delete the file itself.

This is not tidying. It is the difference between a test that exercises the real
undeclare path and one that simulates it — the third defect of that exact shape
in this phase.
</design_decision>

<interface_context>
**The harness (`live_rig_module_injection.rs`, 407 lines) — read it in full.**
Four things in it are load-bearing and must not be "cleaned up":

- `adopt_and_build_session` bootstraps auth through the REAL `adopt` action
  (OIDC login, then mint an API token). Basic auth returns 401 against a
  commissioned 8.3 gateway's `/data/api/v1` — observed live twice. `adopt`
  REWRITES an existing profile's auth rather than creating one, which is why the
  helper seeds the profile first.
- `healthy_module_ids` retries `MODULE_LIST_ATTEMPTS` (20) times at
  `MODULE_LIST_INTERVAL_S` (3s) and CARRIES the error through the loop instead of
  swallowing it. An empty list and a failed call look identical from outside, and
  confusing them sends you debugging module loading when the problem is auth.
  Its current success condition is "the git module is present" — §D needs the
  opposite polarity, so it needs a sibling, not an edit.
- Teardown is UNCONDITIONAL and runs `down -v` plus
  `KeyringStore.delete(LIVE_PROFILE)`. The test mints a real token into the
  operator's macOS keychain; both were verified gone after the 16-03 run.
- `live_enabled()` requires `IGNITION_LIVE_RIG_MODULES == "1"`; unset is a green
  no-op (D-20).

Sections A, B and C run as ONE `#[tokio::test]` in order, because Rust does not
guarantee test ordering and §B's point is that it runs against §A's state. §D and
§E continue that numbering inside `run_sequence`.

**Pitfall 4 (live-observed, 19-RESEARCH).** Immediately after a `rig up` that
recreates the container, a previously-adopted API token can 401 for roughly 10-20
seconds before settling — observed twice. Any §D/§E call that follows a recreate
must tolerate that: the existing retry-carrying-error loop shape already does,
and any new helper must keep it rather than failing fast on the first 401.

**Live fact 2 — the ordering that makes §D possible.** Uninstall REFUSES
(`success:false`) while the module's `.modl` is still bind-mounted. Once the
module is undeclared and the mount is gone, the gateway keeps a GHOST registry
entry — present in `/modules/healthy`'s id list with an EMPTY `name`/`version`
and no `state` key at all — and uninstalling THAT succeeds immediately, no
restart. So §D must run after §C, never before.

**Live fact 3 — there is no undo.** After a successful uninstall, re-declaring
and re-mounting does NOT bring the module back: no healthy entry, no quarantine
entry, not even a "Starting up module" log line. §D is therefore the LAST thing
the sequence can do to those two modules; nothing after it may assume they are
recoverable.

**From 19-01:** `actions::rig::rig_module_uninstall(api, rig, spec)` takes a
`&'static ModuleSpec` and issues ONE call for its `gateway_module_id`.
**From 19-02:** `provision_modules` / `undeclared_provisioning` return a
`ModuleProvisioning` carrying `orphaned_modules`; `rig_up`'s result carries them
too.
</interface_context>
